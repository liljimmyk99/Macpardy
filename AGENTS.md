# AGENTS.md

Guidance for AI coding agents (and humans) working in this repo. Read this first, then the
docs it points to for the area you're changing.

## What this is

**Macpardy** is a native macOS app for hosting a Jeopardy-style trivia game ("Macpardy!")
for a room of people. The host runs the game from a **Control** window on their laptop and
shows a **Display** window on a TV or projector. Teams can buzz in from their phones through a
web page the app serves on the local network.

- Swift / SwiftUI, macOS 26.3+, sandboxed, no backend. Everything runs on the host's Mac.
- One external dependency in the app: [ZIPFoundation](https://github.com/weichsel/ZIPFoundation)
  (board packages). The self-hosted buzzer server also uses [SwiftNIO](https://github.com/apple/swift-nio);
  the app doesn't link it.
- The Xcode project is generated by [Tuist](https://tuist.io) from `Project.swift`.
  `Macpardy.xcodeproj` / `.xcworkspace` are git-ignored; never commit them or edit them by hand.

## Build, run, test

Requires macOS with Xcode 26 (for the macOS 26.3 SDK) and Tuist.

```sh
tuist generate            # creates Macpardy.xcodeproj and opens it
tuist generate --no-open  # same, without opening Xcode

# Unit tests from the command line
xcodebuild test \
  -project Macpardy.xcodeproj \
  -scheme Macpardy \
  -destination 'platform=macOS'

# Buzzer core package tests (not part of the Xcode scheme; CI also runs them on Linux)
swift test --package-path Packages/MacpardyBuzzer

# Self-hosted buzzer server, locally and in Docker (see Packages/MacpardyBuzzer/README.md)
MACPARDY_HOST_TOKEN=<16+ chars> swift run --package-path Packages/MacpardyBuzzer macpardy-buzzer-server
docker build -t macpardy-buzzer-server Packages/MacpardyBuzzer
node Packages/MacpardyBuzzer/scripts/smoke-test.mjs http://127.0.0.1:8472 <token>

# Release build + ad-hoc signed .app and .dmg (see EXPORTING.md)
./scripts/export.sh
```

Re-run `tuist generate` after adding, moving, or deleting files: sources are picked up by glob
(`Macpardy/**/*.swift`, `MacpardyTests/**/*.swift`), but the generated project is a snapshot.

If you can't run macOS tooling (e.g. a Linux sandbox), say so in your PR instead of claiming
the build or tests pass.

## Conventions

### Swift and concurrency
- **Default actor isolation is `MainActor`** (`SWIFT_DEFAULT_ACTOR_ISOLATION`), with
  approachable concurrency on. Pure logic that has to run off the main actor (parsers,
  package reading) is marked `nonisolated`, as in `BoardPackage`. Follow the same pattern for
  new pure types. The buzzer rules (`BuzzerRoom`, the engine, books, messages) are in the `BuzzerCore`
  package instead, which has no default isolation (see
  [External buzzer server](#external-buzzer-server-in-progress-99)).
- Shared observable state uses the Observation framework (`@Observable` classes passed with
  `.environment(...)`), not `ObservableObject`.
- Long-lived I/O lives in `actor`s (`BuzzerServer`, `GameSaveStore`).
- Prefer small value types and `enum` namespaces with static functions for stateless services
  (`BoardLoader`, `CSVBoardImporter`, `ImageImporter`, `BuzzTieResolver`).
- Keep the logic testable outside SwiftUI: rules belong in models/services
  (e.g. `BuzzerEngine`, `FinalWagerBook`, `BoardDraft.makeBoards()`), views call into them.

### SwiftUI view layout
Views are split into a folder per screen:

```
SomeView/
  SomeView.swift              # the struct, its state, and a short `body`
  Components/                 # subviews used only by this screen
  Extensions/SomeView+Extension.swift  # computed properties / @ViewBuilder helpers for body
```

Put new screens and subviews in this shape. Shared pieces go in `Views/Shared/`. Colors and
fonts come from `MacpardyTheme`, not literals. Colors are defined as color sets in
`Assets.xcassets` (`Theme/`, `Team/`) and read through the Tuist-generated `MacpardyAsset`;
add a new color there, then expose it on `MacpardyTheme`. Fonts are SF Pro (the system font),
so they're sizes/weights on `MacpardyTheme`, not bundled files.

When you add or change a `.keyboardShortcut`, update the shortcut tables in
`docs/features.md` (§7) and `README.md`.

### Strings and localization
- **All user-facing text goes in `Macpardy/Localizable.xcstrings`.** Use dotted keys scoped
  by screen: `launch.button.new_game`, `control.question.button.reveal_answer`,
  `create.question.image_error.too_large`, shared ones under `common.*`.
- Pass keys as `LocalizedStringKey` in views, or `String(localized:)` in code.
- English is the only language today; don't add hardcoded English strings in new code.
- Exceptions: CSV column headers are fixed English identifiers by design (see `csv-import.md`).

### Naming
- The app, target, and in-game brand are all **Macpardy** (`MacpardyBoard`, `MacpardyRound`,
  `.macpardy` files, "Final Macpardy"). The old "Macpardy" spelling was retired; don't
  reintroduce it.
- Rounds are `macpardy`, `doubleMacpardy`, `finalMacpardy`.

### Logging
Use `AppLogger` (`Services/AppLogger.swift`) with the matching category: `control`,
`display`, `database` (storage/files), `buzzer`, `network` (the Mac's own network). Don't
use `print` or a raw `os.Logger`. Messages are plain `String`s, written unredacted to the
system log and to the app's own log (Logs window, exports), so don't log Final answers or
anything more personal than team names, local IPs and browser versions. Pass `team:` / `remote:` on buzzer
lines about one phone so the Logs window can filter them.

**Verbose log (#87).** Every tap, menu command, shortcut, window/sheet change, phone action
and model state change also gets a `.debug` line (hidden at the Logs window's default Info
level, but saved and exported). See [`docs/architecture.md`](docs/architecture.md#verbose-log).
- In `Views/`, use `LoggedButton` / `.onLoggedTapGesture` instead of `Button` /
  `.onTapGesture`, with a location like `"Control › Timer › Pause"`. Menu items pass
  `source: .menu`; a key press is detected and logged as `shortcut:` on its own. The
  `unlogged_tap` SwiftLint rule (`.swiftlint.yml`, run by a build phase when `swiftlint` is
  installed) fails the build otherwise. Opt out only with
  `// swiftlint:disable:next unlogged_tap - <reason>`. `Views/Logs/` is exempt.
- Add `.logPresentation(_:isPresented:)` to sheets, alerts, dialogs, popovers and file
  pickers, and `.logCommit(_:text:)` to text fields (it logs the length, never the text).
- Log model changes where they happen, as `log.change("Type.field", from: old, to: new)`
  (skipped when equal) or `log.state("…")` from intent methods that know the reason.
  Conform new models to `LogDescribable` for a safe one-line form.
- Never log clue text, answer text, typed editor text or Final answers. Commit points only:
  no per-keystroke or per-tick lines. Log text is developer English, not localized.
- Tests can check what was logged with `LogCapture.capture { … }` (Debug builds).

### Tests
- XCTest, in `MacpardyTests/`, one file per type under test (`<Type>Tests.swift`), classes
  marked `@MainActor`, `@testable import Macpardy`.
- Tests for `BuzzerCore` live in `Packages/MacpardyBuzzer/Tests/BuzzerCoreTests/`
  (`@testable import BuzzerCore`, no `@MainActor`) and run with `swift test`.
- Add tests for any new parsing, validation, or game/buzzer rule. Inject time, randomness,
  and directories (see `BuzzTieResolver`'s `randomIndex`, `GameSaveStore(baseDirectory:)`)
  instead of depending on the real ones.
- `TestImages.swift` has helpers for building image fixtures.

### Sandbox and entitlements
The app is sandboxed with only: user-selected file read/write, and network server + client
(for the buzzer server). The client entitlement is there only because a sandboxed
`NWListener` can't accept connections from other devices without it; the app doesn't make
outgoing connections, so don't add features that do. The one planned exception is the
external buzzer server (#99): the app may connect out to the server URL the host entered,
and only while the external server is turned on in Settings > Buzzers. See
[External buzzer server](#external-buzzer-server-in-progress-99). Don't add features that need
new entitlements without calling it out in the PR; `scripts/export.sh` checks the exact set.
Files the user picks must be read with security-scoped access (see `FileManagerService`).

### File formats are a contract
Saved boards and auto-saves outlive app versions. When changing `MacpardyBoard`, `Question`,
`QuestionImage`, `GameSnapshot`, or the buzzer messages:
- Keep old files loading (new fields optional / defaulted); bump `BoardPackage.formatVersion`,
  `GameSnapshot.currentSchemaVersion`, or `BuzzerConstants.protocolVersion` only for breaking
  changes.
- Update the matching doc (`board-format.md`, `buzzer-protocol.md`) and `buzzer.html` in the
  same PR.

## External buzzer server (in progress, #99)

The buzzer server is moving out of the app into a Swift package that runs either inside the
app (**built-in**, the default) or as a **self-hosted** Docker server that phones reach over
the internet. Tracking issue: #99. Phases, in order: #100 extract the core, #101 split
`BuzzerServer` into `BuzzerRoom` and a transport, #102 `BuzzerBackend` in the app, #103 the
self-hosted server, #104 connect the app to it, #105 docs, CI, release and the repo move.

Decisions made. Build to these; don't reopen them in a PR without asking:
- **Location.** The package lives in `Packages/MacpardyBuzzer` (a local Tuist package) while
  the work is in progress, then moves to its own repo once all phases are done.
- **Two modes.** The built-in server stays the default and is for phones on the same network
  as the Mac. The self-hosted server is opt-in (Settings > Buzzers: server URL and host
  token) and is for phones on other networks. Don't add support for playing on the
  self-hosted server's own network (NAT loopback); those players use the built-in server.
- **Game PIN.** The self-hosted server owns the PIN and sends it to the host for display. The
  join URL and QR code are built from the server URL the user entered.
- **Rooms.** One self-hosted server runs several rooms, keyed by PIN. A phone's `join` picks
  the room by its `code`.
- **Host drops.** The room is kept for a grace period of 30–60 seconds so the Mac can
  reconnect and resync. After that the server sends `sessionEnded` to every phone and
  closes the room.
- **Security.** Opening a room needs the host token. It only travels over `wss://`, is
  stored in the Keychain, and is never logged. The server limits rooms and phones, and its
  per-IP rate limits can trust `X-Forwarded-For` behind the reverse proxy.
- **Deployment.** The server is a Docker image behind a reverse proxy that handles HTTPS
  (for example Caddy and Let's Encrypt in front of a DuckDNS name). `buzzer.html` uses
  `wss://` when the page is served over `https:`.
- **Protocols.** The Mac-to-server channel gets its own host protocol and version. The phone
  protocol stays at v10 unless the wire format changes.
- **Privacy.** The self-hosted server follows the same logging content rules as the app: no
  clue text, answer text, Final answers or host token.
- **Network transport (decided in #103).** The built-in server stays on Network.framework
  (`BuzzerServer` in the app); the self-hosted server uses SwiftNIO (`BuzzerServerNIO`).
  Moving the built-in server to NIO would only be worth it for one code path; it isn't
  planned.
- **Phone page.** `buzzer.html` lives in the package (`Sources/BuzzerWebPage/Resources/`)
  and both servers serve it. It opens `wss://` on its own host when loaded over `https:`.

While this is in progress:
- Package code is Foundation-only (no `Network`, `AppKit`, `OSLog` or `CommonCrypto` in
  `BuzzerCore`, `BuzzerHostProtocol` or `BuzzerHub`) so it builds on Linux; only
  `BuzzerServerNIO` and the executable import SwiftNIO. It logs through an injected logging
  protocol that the app connects to `AppLogger` and the server to stdout, not through
  `AppLogger` directly.
- Package types are `public` and `Sendable`. The package doesn't use the app's default
  `MainActor` isolation.
- `BuzzerRoom` and `BuzzerHub` have no I/O (#101, #103). It reaches phones only through `BuzzerConnection` and reads
  the time and schedules timers only through its `BuzzerScheduler`, never `Date()` or
  `Task.sleep`, so its tests run on a test clock. Network code stays in the transport
  (`BuzzerServer` and `ClientSession` in the app, `BuzzerServerNIO` for the self-hosted server).
- The host protocol (`BuzzerHostProtocol`) has its own version,
  `BuzzerHostConstants.hostProtocolVersion`. Change it like a file format: update
  `buzzer-protocol.md` in the same PR, and bump it only for breaking changes.
- Tests for code that moves into the package move with it and run with `swift test`.
- Keep `BuzzerState`'s public API stable, so views don't change while the backend changes
  under them.
- `BuzzerState` reaches the server only through `BuzzerBackend` (#102); the built-in server is
  `EmbeddedBuzzerBackend`. New game commands go on the protocol, and any state a fresh server
  needs goes in `BuzzerState.resync()`. Test `BuzzerState` with `FakeBuzzerBackend`.

## Workflow

- Work is tracked in GitHub issues. Branches are named `feat/<short-name>` (or
  `feat/<short-name>-<issue>`); docs-only branches `docs/<short-name>`.
- To release, bump `MARKETING_VERSION` in `Project.swift` in its own PR, merge it, then
  run the **Release** workflow on `master` by hand; it tags, builds and publishes the
  GitHub release (see `EXPORTING.md`). Don't create release tags by hand.
- Commit messages and PR titles follow Conventional Commits: `feat: …`, `fix: …`, `docs: …`.
- PR descriptions: start with `Closes #<n>.`, then **What changed**, behaviour changes the
  reviewer should know about, and anything deliberately left out.
- Update docs in the same PR as the behaviour they describe, including this file when a
  convention changes.
- Don't commit generated or build output (`Derived/`, `build/`, `*.xcodeproj`).
